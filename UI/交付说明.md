## 第十九轮修订（2026-10-27）：双极工作台

- **布局**：≥1024px 左右两栏并排，每栏「今日 / 本周 / 记录」三个视图、独立滚动；底部"合"区放双极环（本周有记录天数占比）、今日数字与同期对照。手机/平板 <1024px 两张卡片上下叠放，前卡占视口减去 88px 预览条，点后卡露出的摘要条交换位置。
- **内容迁移**：原首页的训练计划、负荷、最近记录进运动栏；三餐、类别覆盖、完整/部分记录、本周类别结构进饮食栏。计划 / 跟练 / 饮食 / 周报仍是可下钻的深页，导航脊与底栏同步改名为「两仪」。
- **每日养生**：每次整页进入时以弹窗出现；X 只关这一次，「今日不再出现」按本机日期记住；关闭后落到左侧导航下方的「养生」小卡片，点开为贴着导航浮在主页上的小卡（无遮罩，可展开详解）。手机端小卡在抽屉底部，点开时先收起抽屉。清除全部数据会一并清掉该日期标记。完整对照的免责清单仍在协同弹层。
- **导航分组**：左侧图标脊按「运动 → 计划 / 跟练」「饮食 → 记录」分成两级，组标题带极色圆点并在当前组点亮；「两仪」「周报」留在一级；首页「两仪」只在精确停在 `/` 时高亮。手机抽屉同一套分组。
- **联动口径**：新增 `services/bridgeRules.ts`，只做同期对照——训练了但餐食没记、记了餐食但运动没记、两边都空、两边都记、本周只有一极、训练日与无训练日类别覆盖差（样本 ≥2 天才给）。任一天报了不适，安全提示排最前，文案明确"不会据此建议加量/改餐"；所有结论带"同期出现，不代表因果"。`selfcheck` 第 12 节 29 项断言。
- **验证**：`typecheck` / `build` / `selfcheck`（272 项）通过；无头 Chrome 在 1440 / 1024 / 768 / 390 四个宽度截图，1024 / 768 / 390 横向溢出均为 0；另测深色、空档案与协同弹层。截图在 `redesign-shots/ui/poles-*.png`。
- **未验证**：真机触控、交换后的 Tab 顺序与读屏；`npm run dev` 下 MediaPipe worker 仍按既有边界回落主线程（见 `plan.md` §3）。

## 🎉 已完成工作总结

我已经为您的"两仪·TwoPoles"项目成功创建了一个现代化、专业的前端UI框架。根据您的要求，实现了以下特性：

### ✨ 实现的设计风格（UI 3.0「编辑式仪表盘」）

**1. 纸面 + 单一强调色** ✅（第十八轮定；第十一轮的"冷灰底"已被这一轮替换）
- 底 `#f2f1ec`（中性纸面，不是 SaaS 冷灰）、卡 `#ffffff` + 1px 发丝线 `rgba(17,22,26,.10)`、圆角收到 6–16px、卡片不再靠分层阴影"浮起来"
- 强调色仍只有 `#0f766e` 一种，只用于交互 / 进度 / 已达成；第二极 `#24586f` 只给"饮食"这条数据线，不再参与装饰
- 状态永远"形状 + 文字"双编码：实心＝完整、半填＝部分、空心＝未记录（`ShapeState`），色觉障碍下同样可读
- 装饰渐变只剩品牌位（两仪标志的两极、深色仪表面板的细网格）

**2. 数字是第一主角** ✅
- 数字单独一套字体 `--font-num`（Bahnschrift → DIN 骨架，Windows 自带），44–64px、等宽数字、`letter-spacing: -.045em`
- 小标签统一 `.micro`：10px + `.17em` 字距 + 全大写 + Bahnschrift，中文自动回退到系统字
- 指标从"四张等宽卡"改成一条**指标条**（`StatStrip`）：强横线打头、发丝线分隔，数字竖着能比

**3. 全站只有两种表面** ✅
- 纸面：`BaseCard variant="default"`（自带内距）与 `"flush"`（自带表头/行，内距走 `--card-pad`）
- 仪表面：`BaseCard variant="ink"`——深墨底 + 细网格，只给承载数据仪表的那一块（首页双极环）
- 悬停只交换边框颜色，不做位移、不做图标旋转（2.x 的"浮起来"手感全部移除）

**4. 动效只在操作之后** ✅（第十三轮的结论保持不变）
- 保留：一次性入场（`slideInUp`/`scaleIn`/`bounceIn`，无延迟）、路由过渡、悬停与按压反馈、计数补间、跟练汇总浮入
- 常驻循环动画仍只有两处，且都只存在于"操作进行中"：演示回放边框扫光、休息阶段徽标脉冲
- `prefers-reduced-motion` 覆盖入场与循环动效；主按钮的悬停扫光已在第十八轮移除

**5. 深色主题：只换令牌** ✅（第十六轮建立，第十八轮跟着新令牌重新取值）
- `html[data-theme]` 整组覆盖令牌，组件零感知；深底不靠投影做层级，改 1px 边框 + 更深底色
- 强调色同色相提亮一档 `#3ec9b6`，前景翻深字 `#08201d`；仪表面在深色下再压暗一档


**6. 摄像头跟练** ⚠️（功能项，不属于视觉风格，留在这里只是不打断阅读；识别已真、计数仍演示）
- 可切"演示回放 / 实时摄像头"两种来源；实时模式用 MediaPipe Pose Landmarker 在本机推理，叠加真实骨架与膝/髋/肘角度，画面不上传
- 识别与计数**尚未联动**：实时模式下计数仍由下面的预设时间线推进，界面提示语已写明
- 需要 `npm run camera:assets` 生成端侧资产，且只在 https 或 localhost 下可用
- 坐站训练完整演示 (2 组 × 8 次, 单组 ~22 秒)
- 站姿弯举时间线 (2×10) 与坐站训练 (2×8) 都可用：页内 chip 或 `?exercise=` 进入
- 包含遮挡事件和置信度变化
- 预设的关键点事件时间线（画面是 SVG 示意图，不是真实关键点渲染）
- 不需要真实摄像头或MediaPipe
- ✅ 暂停/继续、跳过本组、结束并记录、手动修正均可用；组数会推进，组间 6 秒倒计时；结果经 `summarizeSession()` 写入 store 并落盘

## 📌 第十九轮修订（2026-10-18，跟练取景框里的人）

起因是审查时的一句"摄像头这一块还是原来的风格，主要是其中的人物"。即：取景框的**容器**已经是 UI 3.0 的深色仪表面，

改成**剪影 + 姿态骨线**（就是概念图里那种"人"）：

1. **结构**：剪影用厚描边拼出来（圆头 + 胶囊躯干 + 圆柱四肢，`stroke-linecap:round`），骨线、关节点、哑铃、头部关键点环叠在上面；

   坐站训练改为**以脚为支点 `scaleY(.9)`**——整体下蹲、不拆关节，避免出现"断肢"。
3. **按动作切换**：新增 `figureJoint`（读 `findExercise().camera.joint`），与计数用的 `camJoint` 分开——后者只在切到实时模式时才赋值，
   演示模式下会一直是默认值，剪影就会用错姿态。坐站训练不握器械，`knee` 姿态下哑铃直接不渲染。
4. **这一轮自己造的三个坑（都是量出来的，不是看出来的）**：
   - **人物比取景框高 45%**：`.skeleton-overlay` 在 `place-items:center` 的网格里，子元素 `height:100%` 被解析成 **851px**（框只有 580px），

### 续：从平涂剪影改成 3/4 视角的关节骨架

第一版的"人"是**平涂**的：一整块同色剪影，下蹲靠 `scaleY(.9)` 把整张图压扁。用户一句话点破——"整个动作太僵硬了，人物动只是压缩了一下图像"。
这话是对的：压扁不是动作；而且正面视角下**下蹲本来就看不出来**，只能看出"变矮"。

这一版换成三样东西叠加：

1. **3/4 视角**：远侧腿/手臂压暗（`#46505a→#262d33`）、近侧提亮（`#626e79→#333b43`），两套 `linearGradient` 用
   `gradientUnits="userSpaceOnUse"` 共用同一束光——每根 limb 横跨同一条明暗坡，圆柱感就是这么来的。
   近侧肢体再压一层 `drop-shadow`，把它从躯干上"抬"起来，否则前臂贴在胸口会糊成一块。
2. **体积**：躯干不再是等宽胶囊，改成上宽下窄的封闭路径 + 对角渐变；头用偏心 `radialGradient`（高光在左上），一眼能看出是个球。
3. **真关节**：每个关节是一个 `<g>`（骨盆、髋、膝、踝、脊柱、肩、肘），`transform-box:view-box` 让 `transform-origin` 直接写画布坐标。
   下蹲 = 骨盆 `translate(-8,46)` + 大腿 `rotate(15deg) scaleY(.73)`（前折 + 透视缩短）+ 小腿 `rotate(-32deg)`
   + 脚掌 `rotate(30deg)` 压平 + 手臂前摆 14°/9° 作配重。**从"整张图压缩"变成"六个关节各转各的"**，
   过渡是 460ms 带回弹的曲线。弯举同理：前臂绕肘 -168° / -152°（远侧滞后），肩再抬 7°/4°。

一处比例返工：中途头做到 72×80 而躯干只有 82 宽，比值 0.88，看起来像气球；把躯干加宽到 112、头收到 60×68，头宽/肩宽回到 0.54 才像人。
这类问题肉眼能看出"不对"但说不清错在哪，最后是把这个比值算出来才对上的。

**这一版不是 WebGL**，是 2D SVG 的假立体（明暗 + 透视 + 关节点）。真 3D 要引 three.js（约 +150 kB gzip）并维护一套骨骼，
而且实时模式的骨架来自 MediaPipe 的 2D 关键点，两者视觉会打架。要不要走那条路需要单独决策。
